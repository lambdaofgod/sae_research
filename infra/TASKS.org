** How they relate

What stays as-is:
- Activault collection pipeline, Garage S3, Helm chart, monitoring stack

What migrates:
- Training code from =dictionary_learning_demo/= → =sae_research/sae_research/training/=

What gets replaced:
- =demo_config.py= globals → structured YAML configs (=configs/models/=, =architectures/=, =sweeps/=)
- DVC evaluation pipeline → KFP evaluation pipeline
- =parallel_training.py= hardcoded device assignment → Kueue GPU scheduling

- Artifact contract (standard =ae.pt= + =config.json= format between train and eval)
- MLflow server on K8s (PostgreSQL + Garage artifact store)
- Training Operator v2 (=TrainJob= / =ClusterTrainingRuntime= CRDs)
- Kueue (GPU admission control, queuing, quotas)
- Katib (hyperparameter sweep orchestration)
- KFP training pipeline + KFP evaluation pipeline

*** Artifact layout
Each trained SAE lives in ={save_dir}/{submodule_name}/trainer_{i}/= with:

  - =trainer=: full trainer config (backward compatible, used by =load_dictionary()=)

  - core_eval        # KL divergence, CE loss, explained variance, L0
  - sparse_probing   # classification accuracy (top-k probing)
  - absorption       # feature absorption
  - scr              # spurious correlation removal
  - tpp              # targeted perturbation probing
#+end_example

*Current state* — MLflow. Each SAE's child run accumulates eval metric keys
over time. Presence of a metric key = that eval was done.

*Reconciliation* — a KFP pipeline that:
1. Reads the eval config
2. Queries MLflow for all SAE runs
3. Computes the gap: which (SAE, eval_type) pairs are missing
4. Works through gaps sequentially (one GPU — no fan-out)
5. Logs results back to each SAE's MLflow child run

This handles:
- *New SAEs trained* — no metrics yet → gap filled automatically
- *New eval type added* to config — missing everywhere → runs on all SAEs
- *Eval code changed* — user triggers with =--force --eval-types sparse_probing=
  (no automatic staleness detection — would require splitting packages into
  separate training/eval images to track via container digest; not worth it
  for a research project where eval code changes are deliberate and rare)

*Required tags* — all eval logging requires explicit tags to prevent
cross-contamination. At minimum =experiment_name= must be set (e.g.
="topk_vs_batchtopk_march2024"=, ="smoke_test"=). The =log_eval_to_mlflow()=
function enforces this. Tags enable filtering runs by experiment campaign
in MLflow UI and =search_runs()= queries.

*Manual/targeted mode* — same pipeline, optional filter parameters:
- =--experiment-name= (required) → tag for this eval campaign
- =--run-ids X Y Z= → only these SAEs
- =--eval-types sparse_probing absorption= → only these eval types
- =--force= → rerun even if metrics already exist
- No run-ids/eval-types → full reconciliation (discover all gaps)

Can be triggered manually or on a schedule.

** TODO Katib for hyperparameter sweeps
Without Katib, sweeps are =itertools.product()= in =config.py=
=get_trainer_configs()= — generates all combos of seed × dict_width × lr ×
sparsity_penalty and trains them sequentially (or manually split across GPUs
via =parallel_training.py=).

Katib =Experiment= CRD replaces this: define search space, objective metric
(e.g. minimize reconstruction MSE at target L0), algorithm (Bayesian, TPE,
Hyperband). Each trial spawns a TrainJob via Kueue. =parallelTrialCount=
controls concurrent GPU usage automatically.

Concrete search spaces from =config.py=:
- =dictionary_widths=: [2^12, 2^14, 2^16]
- =learning_rates=: [1e-4] (fixed in config, could sweep)
- =TARGET_L0s=: [20, 40, 80, 160, 320]
- =SPARSITY_PENALTIES=: varies per architecture (6 values each)

Structured config format (from config restructuring) maps directly onto
Katib search space definitions.
