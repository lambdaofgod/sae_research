* TODO Fix ~ResilientS3RCache~ shutdown deadlock (root cause)

**Root cause identified** (PID 783351, 5 days hung, 3.5 GB VRAM held):

The runner's main thread is stuck in
~dictionary_learning.activault_s3_buffer.S3RCache._stop_downloading()~
(line 524-542):

#+BEGIN_SRC python
while not all([not p.is_alive() for p in self._running_processes]):
    if not self.readable_tensors.empty():
        self.readable_tensors.get()
    if not self.writeable_tensors.full():
        self.writeable_tensors.put(0)
    time.sleep(0.25)
for p in self._running_processes:
    p.join()
#+END_SRC

This is a *cooperative-only* shutdown: it sets a stop flag and polls.
But the worker subprocesses are async tasks blocked inside
~aiohttp~ reads or shared-memory queue waits — they never see the
stop flag because they're parked in syscalls. The wait loop spins
forever; ~p.join()~ is never reached.

Evidence from PID 783351:
- main-thread wchan: ~hrtimer_nanosleep~ (the ~time.sleep(0.25)~)
- 80 worker threads in ~futex_wait_queue~ (idle daemons, normal)
- 9+ multiprocessing children alive 5+ days (the S3 download workers)
- 49 open pipes (worker IPC), 1 socket, 0 TCP connections
- ~/proc/<pid>/io~: 87 GB written, ~9 GB read — work was real and finished

GPU VRAM is held *as a side effect*: while the main thread is parked
in this shutdown loop, Python references to the model / SAE / buffer
are never released, so CUDA tensors stay live in the allocator.

** Fix options

1. **Hard timeout + ~terminate()~** in our ~ResilientS3RCache~:
   override ~_stop_downloading~ to wait at most N seconds, then
   ~p.terminate()~ + ~p.kill()~ stragglers.
2. **Daemonize the workers** (~Process(daemon=True)~ in
   ~ResilientS3RCache.__iter__~) so they die with the parent on
   normal interpreter exit. Doesn't fix the explicit-cleanup path
   but rescues the "user Ctrl-C / process exits" case.

Do (1) + (2) — belt and suspenders.

** Operational note

Until fixed, audit before launching long jobs:
~ps -ef | grep training.runner~ and kill stragglers — they leak GPU
memory and break later eval runs (this is exactly what just blocked
the Qwen-Scope comparison).

* TODO Support Qwen 3.5 models (and Qwen-Scope SAEs) in the eval pipeline

Goal: load Qwen3.5-9B + Qwen-Scope pretrained SAEs through the same
~sae_research/eval/components.py:run_core_eval~ path we use for our own
SAEs, and remove the standalone ~qwen_scope_saes/~ subproject.

Loading recipe (HF-direct, used during Qwen-Scope training and verified
to work in this venv) is documented in ~qwen_scope_saes/HOWTO.org~.

** Background

- ~transformer-lens~ ~main~ (~v3.1.0~) ships
  ~Qwen3_5ArchitectureAdapter~ in
  ~transformer_lens/model_bridge/supported_architectures/qwen3_5.py~
  and dispatches it via ~TransformerBridge.boot_transformers~.
- The legacy ~OFFICIAL_MODEL_NAMES~ registry (used by
  ~HookedTransformer.from_pretrained_no_processing~) does *not*
  include Qwen3.5 — only Qwen3 and below.
- ~sae-bench~ core eval loads the LLM at
  ~sae_bench/evals/core/main.py:1034~ via
  ~HookedTransformer.from_pretrained_no_processing(sae.cfg.model_name, ...)~
  → registry path → fails for Qwen3.5.
- The ~TransformerBridge~ exposes every API ~sae-bench~ relies on
  (verified on Qwen3-0.6B): ~W_E~, ~tokenizer~, ~cfg.device~,
  ~model(..., return_type='both', loss_per_token=True)~,
  ~run_with_cache(..., prepend_bos=False, names_filter=[...], stop_at_layer=N)~,
  ~run_with_hooks~.
- Bridge's default behavior is raw HF weights (no LN folding, no
  weight centering) — same semantics as ~from_pretrained_no_processing~.
